## 〈 요약문 〉

### 프로젝트 목표

본 프로젝트의 목표는 고서(한문/한글 고문서) 이미지를 OCR과 AI를 통해 자동으로 번역하고, 커뮤니티 게시판에서 고서 관련 질문과 토론이 이루어지는 통합 플랫폼을 구축하는 것이다. OCR 엔진과 AI 모델을 인터페이스로 추상화하여 교체 가능하도록 설계하며, 고서 번역기와 커뮤니티 게시판을 핵심 시스템으로 제공한다.

### 내용

본 시스템은 PaddleOCR을 통해 고서 이미지에서 한자/한글 텍스트를 추출하고, Gemini Flash AI 모델을 활용하여 직역과 의역을 분리 제공한다. 커뮤니티 게시판에서는 AI 자동 답변 기능으로 응답 공백을 줄이고, 악성댓글 AI 필터링으로 건전한 커뮤니티 환경을 유지한다. 고서 번역기는 이미지/텍스트 입력 → OCR → AI 번역 → 요약/키워드 추출까지의 파이프라인을 제공하며, 번역 결과의 사용자 수정을 통해 집단 지성 기반의 품질 향상을 도모한다.

### 기대효과

- 한문 고서에 대한 접근성을 높여 일반인과 학생의 고서 학습을 지원
- OCR + AI 번역 파이프라인의 자동화로 전문가 없이도 고서 내용 파악 가능
- 커뮤니티 기반 지식 공유 및 AI 보조를 통한 고서 연구 생태계 조성

### Keywords

고서 OCR, AI 번역, 직역/의역, 커뮤니티 게시판, AI 자동 답변, PaddleOCR, Gemini Flash

## I. 서론

### 1. 프로젝트의 배경 및 필요성

#### 1.1 제안배경

한문 고서는 한국의 역사와 문화를 담고 있는 중요한 자산이지만, 일반인이 접근하기 어려운 영역이다. 전문가 없이는 내용 파악이 불가능에 가깝고, 기존 OCR 서비스는 현대 문서에 최적화되어 있어 고서에 대한 인식률과 번역 품질이 낮다. 또한 고서에 관심 있는 사람들이 질문하고 지식을 공유할 수 있는 전문 커뮤니티가 부재한 상황이다. 이에 본 프로젝트는 OCR과 AI 기술을 활용하여 고서의 접근성을 높이고, 커뮤니티를 통한 집단 지성 기반의 고서 번역 생태계를 구축하는 것을 제안한다.

#### 1.2 기존 서비스의 문제점 분석

**가) 기존 OCR 서비스의 한계**

- 현대 문서(인쇄체, 타이핑 문서)에 최적화되어 있어 고서/고문서 인식률이 낮다.
- 한문(한자) 고서에 대한 전문 OCR 솔루션이 부재하다.
- OCR 결과만 제공하고, 번역이나 해석까지 연계되지 않는다.

**나) 기존 번역 서비스의 한계**

- 범용 번역기(Google 번역, Papago 등)는 고문 한문의 맥락을 제대로 반영하지 못한다.
- 직역과 의역을 분리하여 제공하는 서비스가 없다.
- 이미지 입력 → OCR → 번역까지 연결된 통합 파이프라인이 부재하다.

**다) 커뮤니티 부재**

- 고서 관련 질문/토론을 할 수 있는 전문 커뮤니티가 없다.
- 기존 커뮤니티는 답변까지 시간이 오래 걸리고, AI 보조 기능이 없다.

#### 1.3 필요한 요구사항

**가) 고서 번역 파이프라인**

- 고서 이미지에서 한자/한글을 인식하는 OCR 기능
- OCR 결과를 직역/의역으로 분리 번역하는 AI 기능
- 핵심 요약, 키워드 추출, 단어 빈도수 분석 기능
- 번역 결과 사용자 수정 및 저장/공유 기능

**나) 커뮤니티 게시판**

- 게시글 CRUD 및 댓글 기능
- 일정 시간 내 답글 없을 시 AI 자동 답변 생성
- 악성댓글 AI 필터링

**다) 관리 시스템**

- 게시판별 AI 파이프라인 ON/OFF 관리
- AI 자동 답변 설정 관리
- 사용자 인증/회원 시스템

#### 1.4 프로젝트의 필요성

가) 한문 고서의 높은 접근 장벽을 OCR + AI 자동 번역으로 낮춤으로써, 일반인과 학생도 고서의 내용을 쉽게 파악할 수 있는 환경을 제공한다.

나) 직역/의역 분리 제공과 사용자 수정 기능을 통해, AI 번역의 한계를 집단 지성으로 보완하는 선순환 구조를 구축한다.

다) AI 자동 답변과 커뮤니티를 결합하여, 고서 학습 과정에서 발생하는 질문에 대한 즉각적인 피드백 환경을 마련한다.

### 2. 프로젝트의 범위(요약)

본 프로젝트는 고서 OCR 번역 및 커뮤니티 플랫폼을 구축하는 것을 목표로 하며, 3개의 Phase로 나누어 점진적으로 개발한다.

#### 2.1 주요 개발 범위

**가) Phase 1 - 게시판 + OCR + AI 자동 댓글/답변 (4주)**

커뮤니티 게시판 CRUD를 구현하고, 고서 이미지 업로드 → OCR 텍스트 추출 → AI 직역/의역 자동 댓글 생성 파이프라인을 구축한다. 미응답 게시글에 대한 AI 자동 답변 기능을 포함한다.

**나) Phase 2 - 고서 번역 파이프라인 + 부가 기능 (5주)**

게시판과 독립된 고서 번역기를 구현하고, 번역 수정, 핵심 요약/키워드, 결과 저장/공유, 참고자료 추천 기능을 추가한다. 게시판에 고서 파이프라인 자동 연동 옵션을 제공한다.

**다) Phase 3 - 관리자 페이지 + 회원 시스템 (3주)**

관리자 전용 페이지(파이프라인 ON/OFF, 댓글 관리), 악성댓글 AI 필터링, 사용자 인증/회원 시스템을 구현한다.

#### 2.2 범위 제외 항목

- 모바일 앱 (웹 반응형으로 대체)
- 일본어/기타 언어 고문서 지원
- OCR 모델 직접 학습/파인튜닝
- 논문 파일 자체 호스팅 (링크만 제공)

## II. 프로젝트 수행 내용

### 1. 목표시스템의 구성도

```
┌─────────────────────────────────────────────────────────┐
│                    사용자 (브라우저)                       │
└──────────────────────┬──────────────────────────────────┘
                       │ HTTP
┌──────────────────────▼──────────────────────────────────┐
│                Client (React / Remix)                    │
│   - 게시판 UI / 고서 번역기 UI / OCR 결과 표시            │
│   apps/client                                           │
└──────────────────────┬──────────────────────────────────┘
                       │ REST API
┌──────────────────────▼──────────────────────────────────┐
│                Server (FastAPI / Python)                  │
│  ┌─────────┐ ┌──────────┐ ┌───────────┐ ┌───────────┐  │
│  │ API     │ │ Services │ │ Scheduler │ │ Pipeline  │  │
│  │ Layer   │ │ Layer    │ │           │ │ (OCR+AI)  │  │
│  └─────────┘ └──────────┘ └───────────┘ └───────────┘  │
│   apps/server                                           │
└──────────────────────┬──────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────┐
│            Database (PostgreSQL 16 on Docker)             │
│   posts │ comments │ ocr_results │ translations          │
└─────────────────────────────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────┐
│                    외부 서비스                             │
│   - PaddleOCR / Google Vision API (OCR)                  │
│   - Gemini Flash / Claude Haiku (AI 번역/답변)            │
└─────────────────────────────────────────────────────────┘
```

**가) Client (React / Remix)**

사용자에게 커뮤니티 게시판, 고서 번역기, OCR 결과 표시/편집 화면을 제공하는 웹 인터페이스이다. PC 환경을 우선으로 하되, 반응형 레이아웃으로 모바일 접근도 지원한다.

**나) Server (FastAPI / Python)**

모든 비즈니스 로직을 처리하는 핵심 서버이다. 게시판 CRUD, OCR + AI 번역 파이프라인, AI 자동 답변 스케줄러, 파일 업로드 등을 REST API로 제공한다. OCR 엔진과 AI 모델은 인터페이스로 추상화하여 교체 가능하도록 설계한다.

**다) Database (PostgreSQL 16)**

게시글, 댓글, OCR 결과, 번역 결과 등 모든 데이터를 저장·관리한다. Docker Compose로 운영하여 개발 환경의 일관성을 확보한다.

**라) 외부 서비스**

PaddleOCR(1순위) 또는 Google Vision API(2순위)를 통해 이미지에서 텍스트를 추출하고, Gemini Flash(1순위, 무료) 또는 Claude Haiku(2순위, 유료)를 통해 AI 번역 및 자동 답변을 생성한다.

## III. 결론

### 1. 프로젝트 결과의 활용방안

#### 1.1 고서 학습 지원 도구

고서에 관심 있는 일반인, 대학생, 스터디 그룹이 전문가 없이도 고서의 내용을 파악할 수 있는 학습 도구로 활용한다. 직역/의역 비교를 통해 원문의 뉘앙스를 이해하고, 요약/키워드를 통해 핵심 내용을 빠르게 파악할 수 있다.

#### 1.2 집단 지성 기반 번역 품질 향상

AI 번역 결과를 사용자가 직접 수정하는 기능을 통해, 시간이 지남에 따라 번역 데이터의 품질이 향상되는 선순환 구조를 구축한다. 축적된 데이터는 향후 AI 모델 파인튜닝의 학습 데이터로도 활용 가능하다.

#### 1.3 고서 연구 커뮤니티

고서 관련 질문과 토론이 이루어지는 커뮤니티를 통해, 분산된 고서 지식을 한 곳에 모으는 허브 역할을 한다. AI 자동 답변은 초기 커뮤니티 활성화에 기여한다.

#### 1.4 교육 및 포트폴리오

OCR + AI 파이프라인, 풀스택 웹 개발, 인터페이스 기반 설계 등의 역량을 종합적으로 보여주는 포트폴리오 프로젝트로 활용 가능하다.

## IV. 기타

### 1. 주요 고려사항 및 리스크

#### 1.1 OCR 인식률 한계

PaddleOCR의 고문서 인식률이 현대 문서 대비 낮을 수 있다. 특히 필사본, 훼손된 문서, 비정형 서체 등에서 인식률 저하가 예상된다.

#### 1.2 AI 번역 품질 의존성

AI 모델(Gemini Flash / Claude Haiku)의 한문 이해도에 번역 품질이 크게 의존한다. 고전 한문의 맥락과 문법은 현대 중국어와 다르므로, 번역 정확도가 기대 이하일 수 있다.

#### 1.3 무료 API 제한

Gemini Flash(무료)의 호출 제한(Rate Limit)으로 인해 대량의 번역 요청 처리 시 병목이 발생할 수 있다.

#### 1.4 3인 팀 병렬 개발 리스크

Frontend/Backend/AI Pipeline 간 인터페이스 불일치나 일정 지연이 발생할 경우 전체 일정에 영향을 미칠 수 있다.

---

### 2. 리스크 관리 방안

#### 2.1 OCR 엔진 교체 전략

OCR 엔진을 인터페이스로 추상화하여 PaddleOCR의 인식률이 부족할 경우 Google Vision API로 교체 가능하도록 설계한다. 두 엔진의 인식률을 비교 테스트하여 최적의 엔진을 선택한다.

#### 2.2 AI 모델 이중화

Gemini Flash의 번역 품질이 부족할 경우 Claude Haiku로 전환 가능하도록 AI 번역 인터페이스를 추상화한다. 두 모델의 번역 결과를 비교하여 품질 기준을 설정한다.

#### 2.3 API 호출 제한 대응

Rate Limit 발생 시 요청 큐잉 및 재시도 로직을 적용한다. 필요 시 유료 플랜(Claude Haiku) 전환을 검토한다.

#### 2.4 팀 간 인터페이스 관리

Phase 착수 전 Phase별 상세 SRS를 작성하여 API 스펙과 인터페이스를 명확히 정의한다. 주 1회 이상 팀 동기화 미팅을 통해 일정과 이슈를 공유한다.
