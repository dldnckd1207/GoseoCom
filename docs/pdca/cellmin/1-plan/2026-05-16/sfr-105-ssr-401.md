## 1. 목표 및 범위

SSR loader/action에서 serverFetch 사용 중 access token 만료(401) 발생 시 Refresh Token으로 자동 갱신 후
재시도하거나, 갱신 실패 시 /login으로 안전하게 redirect한다.

**범위:**
- `apps/client/app/shared/api/server.ts` — refresh 로직 추가
- `apps/client/app/routes/_protected.library._index.tsx` — catch에서 Response rethrow 추가
- `apps/client/app/routes/_protected.translate.tsx` — catch에서 Response rethrow 추가
- `apps/client/app/routes/_layout.tsx` — optional auth catch에서 Response rethrow 추가
- `apps/client/app/routes/_layout.community._index.tsx` — ME/BOARDS_LIST/POSTS_LIST catch rethrow 추가
- `apps/client/app/routes/_layout.community.$id.tsx` — ME catch, action catch rethrow 추가
- `apps/client/app/routes/_layout.community.write.tsx` — ME/BOARDS_LIST/action catch rethrow 추가

**범위 외:**
- 클라이언트 사이드 `apiClient` 변경 없음 (이미 구현됨)
- translate action의 multipart 직접 fetch (action에서의 401은 이번 범위 외)
- non-JSON 오류 응답 처리 개선 (별도 이슈)

## 2. 현재 동작 vs 원하는 동작

| 상황 | 현재 | 목표 |
|------|------|------|
| SSR loader 실행 중 access token 만료 | ApiError throw → 빈 화면 | refresh → 성공 시 재시도, 실패 시 /login redirect |
| refresh token도 만료 | — | /login?redirect=현재경로(+query) |
| route catch가 Response를 삼킴 | redirect 전파 안 됨 | `instanceof Response` 가드로 rethrow |

---

## 3. 확정 방안 (방안 B — redirect 방식)

```
serverFetch 401 감지
    ↓
/auth/refresh 호출 (기존 cookie 사용)
    ├─ 실패 → throw redirect('/login?redirect=pathname+search')
    ├─ 성공 + Set-Cookie 없음 → throw redirect('/login?redirect=pathname+search')
    └─ 성공 + Set-Cookie 있음 → 다중 Set-Cookie 포함 현재 URL로 302 redirect
                                  브라우저가 새 cookie로 재요청 → 정상 렌더링
```

## 4. 성공 기준

- [ ] access token 만료 상태에서 SSR 페이지 접근 시 자동 갱신 후 정상 렌더링
- [ ] refresh 후 `access_token` + `refresh_token` Set-Cookie 모두 브라우저에 전달됨
- [ ] refresh token 만료 시 `/login?redirect=pathname+search` (query string 보존)
- [ ] route catch가 redirect Response를 삼키지 않고 rethrow
- [ ] refresh 성공 + Set-Cookie 없음 → 무한 redirect 없이 /login으로 이동
- [ ] 기존 정상 케이스(401 아닌 경우) 동작 변경 없음
- [ ] TypeScript 오류 0, lint 오류 0
