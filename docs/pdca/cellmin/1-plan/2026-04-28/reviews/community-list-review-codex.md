# Review — 커뮤니티 목록 페이지 Plan (#98)

- **Reviewer:** Codex
- **Date:** 2026-04-28
- **Target:** `docs/pdca/cellmin/1-plan/2026-04-28/community-list.md`

---

## Findings

### Medium — 상세/작성 라우트가 성공 기준에 포함되어 있으나 범위가 닫혀 있지 않음

- 대상 위치: `글 작성하기 버튼`, `성공 기준`
- 관련 항목:
  - 로그인 사용자 클릭 시 `/community/write` 이동
  - 게시글 행 클릭 시 `/community/:id` 이동

현재 Plan은 `/community` 목록 페이지 구현을 목표로 잡고 있으며, 파일 구조도 목록 라우트와 목록 View만 포함한다. 하지만 성공 기준에는 `/community/write`, `/community/:id` 이동이 포함되어 있다.

이 두 라우트가 아직 존재하지 않는 상태라면 구현 후 클릭 검증 시 404 또는 미구현 화면으로 이어질 수 있다.

권장:

- #98 범위가 목록 페이지에 한정된다면 성공 기준을 "대상 URL로 navigate/link 설정" 수준으로 낮춘다.
- 실제 이동까지 검증해야 한다면 write/detail 라우트 스텁 생성까지 범위에 포함한다.

### Medium — 페이지네이션 기대값이 목업과 충돌할 수 있음

- 대상 위치: `성공 기준`
- 관련 항목:
  - 목업 디자인(`community.html`) 기준 UI 일치

목업은 페이지네이션 버튼 1, 2, 3을 표시한다. 반면 Design 문서의 mock 데이터 계획은 총 20개, `PAGE_SIZE = 10`이라 실제 구현에서는 2페이지만 표시된다.

권장:

- 목업과 동일하게 3페이지 버튼을 보여야 한다면 mock 데이터를 30개 이상으로 맞춘다.
- 동적 페이지 수 렌더링이 의도라면 "목업의 시각 스타일을 따르되 페이지 수는 데이터에 따라 변동"이라고 성공 기준을 조정한다.

### Low — API 전환 지점은 더 명확히 쓰는 편이 좋음

- 대상 위치: `목표 & 범위`
- 관련 항목:
  - Mock 데이터 사용 → 백엔드 완성 후 loader에서 API 호출로 교체

현재 단계에서는 mock 데이터를 클라이언트에서 필터링하는 방향이 적절하다. 다만 Design 문서는 별도 child loader 없이 구현한다고 되어 있으므로, 이후 API 전환 시점에 loader 추가가 필요하다는 점을 Plan에도 명확히 남기면 좋다.

권장 문구:

> 이번 #98 구현은 별도 목록 loader 없이 mock 데이터를 사용한다. 백엔드 API 연동 시 `_layout.community._index.tsx`에 child loader를 추가하고 필터/페이지네이션 쿼리를 서버 요청 파라미터로 전달한다.

---

## 좋은 점

- 공개 라우트로 `_layout`을 사용하는 방향은 현재 앱 구조와 맞다.
- 필터와 페이지 상태를 URL 쿼리스트링으로 관리하는 요구사항은 새로고침, 뒤로가기, 링크 공유 측면에서 적절하다.
- 검색 기능과 실제 API 연동을 범위 제외로 둔 점은 #98의 구현 범위를 작게 유지하는 데 도움이 된다.

---

## 제안 수정 요약

- `/community/write`, `/community/:id`를 이번 범위에 포함할지 결정한다.
- mock 데이터 개수와 페이지네이션 버튼 기대값을 맞춘다.
- API 연동 전환 시 child loader를 추가한다는 메모를 Plan에 남긴다.

---

## 재검토 — 2026-04-28 수정본

### 반영 확인

- API 전환 시 `_layout.community._index.tsx`에 child loader를 추가하고 필터/페이지네이션 쿼리를 서버 파라미터로 전달한다는 내용이 추가됨.
- 페이지네이션 기준이 Mock 30개, 3페이지 표시로 정리됨.
- `/community/:id` 라우트 스텁이 #98 범위에 포함됨.
- 글 상세 구현(#99), 글 작성 구현(#100)은 범위 제외로 분리됨.

### 남은 확인 사항

#### Low — `/community/write`는 navigate만 검증하는지, 스텁까지 둘지 결정 필요

- 대상 위치: `글 작성하기 버튼`, `성공 기준`

수정본에서는 로그인 사용자가 글 작성하기 클릭 시 `/community/write`로 `navigate`한다고 표현되어 있다. 동시에 글 작성 구현은 #100 범위로 제외되어 있다.

현재 문서 상태라면 "URL 변경만 검증"하는 기준으로는 일관성이 있다. 다만 브라우저 수동 검증에서 실제 화면 도달까지 확인하려면 `/community/write` 스텁 라우트도 필요하다.

권장:

- #98에서는 URL 변경만 검증한다면 현재 표현을 유지한다.
- 404 없이 화면 전환까지 확인하려면 `routes/_layout.community.write.tsx` 스텁을 파일 구조와 범위 포함 항목에 추가한다.
