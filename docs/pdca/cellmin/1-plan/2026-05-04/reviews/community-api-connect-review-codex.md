## 총평

Plan 문서는 커뮤니티 목록/상세 화면의 Mock 데이터를 실제 게시판 API로 교체한다는 목표와 필수 변경 파일을 명확히 잡고 있다. SFR-105의 다중 게시판과 SFR-101의 게시글/댓글 API를 연결하는 작업 범위도 현재 코드 구조와 대체로 맞다.

다만 구현 착수 전 성공 기준과 예외 범위를 조금 더 구체화하는 편이 좋다. 특히 `all` 탭의 페이지네이션 정책, 질문 게시판 비로그인 접근 차단의 처리 위치, 게시글 작성 페이지 제외 범위는 문서상 명확히 고정되어야 구현 중 요구사항 해석이 흔들리지 않는다.

## 발견 사항

### High - `all` 탭 페이지네이션 성공 기준이 불명확함

FR-2는 `all` 탭 선택 시 API 조회를 요구하지만, BE는 `board_code` 필수 목록 API만 제공한다. Design 문서에서는 게시판별 조회 후 합산 전략을 제시하고 있으나, Plan의 성공 기준에는 전체 탭에서 여러 게시판의 2페이지 이후 데이터를 어떻게 다룰지 정의되어 있지 않다.

`all` 탭을 1페이지 최신글 모음으로 제한할지, 게시판별 over-fetch 후 병합 페이지네이션을 제공할지 Plan에 명시하는 것이 좋다.

### High - 질문 게시판 비로그인 접근 차단 범위가 목록 중심으로만 보임

FR-3은 "질문 게시판 접근 차단"을 말하지만 성공 기준은 "질문 탭 접근 차단 메시지"에 가깝다. 실제로는 `/community/:id` 상세 URL로 질문 게시글에 직접 접근하는 경우도 포함되어야 한다.

성공 기준에 "비로그인 사용자가 질문 게시글 상세 URL로 직접 접근해도 접근 제한 화면을 본다"를 추가하는 것이 좋다.

### Medium - 게시글 작성 페이지 제외 범위 명시 필요

선택 범위에 `_layout.community.write.tsx`가 있으므로 이번 작업에서 게시글 작성 API 연결은 제외로 보인다. 하지만 목표가 "Mock 데이터를 제거하고 실제 백엔드 REST API로 교체"인 만큼, 사용자는 글 작성 버튼/작성 페이지까지 포함된다고 해석할 수 있다.

이번 사이클에서는 댓글 작성만 포함하고 게시글 작성은 제외한다는 점을 비기능 요구사항 또는 제외 범위에 명시하는 것이 좋다.

### Medium - 에러/빈 상태 성공 기준 보강 필요

성공 기준은 정상 조회 중심이다. API 403/404/네트워크 오류 시 어떤 화면을 보여줄지 최소 정책이 필요하다.

- 질문 게시판 403: 접근 제한 메시지
- 게시글 404: 라우트 에러 또는 Not Found
- 목록 API 실패: 에러 화면 또는 빈 목록 처리
- 댓글 작성 실패: 폼 하단 에러 메시지

## 확인 완료 항목

- `posts/list`, `posts/{id}`, `comments/list`, `comments` API 연결 범위가 SFR-101과 일치
- `translation`, `questions`, `free` board_code 매핑 필요성이 SFR-105 seed 게시판과 일치
- Mock 파일은 삭제하지 않고 import만 제거한다는 정책이 기존 FE 작업 흐름과 호환
- TypeScript 타입 체크를 성공 기준에 포함한 점은 적절함

## 권장 보완

- 성공 기준에 질문 게시글 상세 직접 접근 차단 추가
- `all` 탭의 페이지네이션 정책을 Plan 단계에서 결정
- 게시글 작성 페이지/API 연결은 이번 범위 제외라고 명시
- API 실패 시 사용자에게 보여줄 최소 상태를 성공 기준 또는 요구사항에 추가

## 결론

Plan 문서는 구현 착수 기준으로 큰 방향은 충분하다. 다만 위 보완 사항 중 `all` 탭 정책과 질문 상세 접근 차단은 구현 결과에 직접 영향을 주므로, Design 반영 전에 먼저 확정하는 것을 권장한다.
