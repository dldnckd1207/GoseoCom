## 〈 요약문 〉

### 프로젝트 목표

본 프로젝트의 목표는 기존 LSTM 기반 단일 주가 예측 프로그램을 현대적인 퀀트 트레이딩 시스템으로 재설계하는 것이다. GPU 없이 CPU만으로 동작하는 한국 주식(KOSPI/KOSDAQ) 대상 스윙 트레이딩 시스템을 구축하며, 데이터 수집부터 기술적 분석, 전략 수립, 백테스팅, 시각화까지 전 과정을 아우르는 통합 파이프라인을 제공한다.

### 내용

본 시스템은 pykrx를 통해 한국거래소(KRX) 공식 일봉 데이터를 수집하고, RSI·MACD·볼린저밴드 등 기술적 지표를 산출하여 룰 기반 및 머신러닝(LightGBM) 기반 매매 전략을 실행한다. vectorbt 엔진을 활용한 백테스팅으로 전략의 성과를 검증하며, Streamlit 대시보드를 통해 차트·신호·성과 리포트를 시각적으로 제공한다. 인터페이스 기반 설계를 적용하여 데이터 소스, 전략, 백테스트 엔진을 독립적으로 확장할 수 있도록 구성한다.

### 기대효과

- 레거시 시스템(LSTM+Tkinter)의 한계를 극복하고 확장 가능한 현대적 아키텍처 확보
- 다양한 매매 전략의 객관적 성과 비교를 통한 데이터 기반 투자 의사결정 지원
- 룰 기반 전략과 ML 전략의 비교 분석으로 퀀트 투자 연구 기반 마련

### Keywords

퀀트 트레이딩, 백테스팅, 기술적 지표, 룰 기반 전략, LightGBM, 스윙 트레이딩

## I. 서론

### 1. 프로젝트의 배경 및 필요성

#### 1.1 제안배경

개인 투자자의 주식 투자 의사결정은 대부분 감에 의존하거나, 단편적인 기술적 분석에 머무르는 경우가 많다. 체계적인 퀀트 전략 기반의 투자 시스템은 기관 투자자에게는 보편화되어 있지만, 개인 투자자가 직접 구축하기에는 진입 장벽이 높다. 이에 본 프로젝트는 한국 주식 시장에 특화된 경량 퀀트 트레이딩 시스템을 구축하여, 데이터 기반의 객관적인 매매 판단을 지원하는 것을 제안한다.

#### 1.2 기존 시스템의 장점 및 문제점 분석

**가) 기존 시스템(LSTM 기반)의 장점**

- TensorFlow/Keras 기반 딥러닝 모델을 활용하여 시계열 예측을 시도하였다.
- Tkinter GUI를 통해 사용자 인터페이스를 제공하였다.
- FinanceDataReader를 통해 기본적인 데이터 수집이 가능하였다.

**나) 기존 시스템의 문제점**

- 단일 종목의 **종가 예측**에만 집중하여, 실질적인 매매 전략과 연결되지 않는다.
- LSTM 모델은 **GPU 의존성**이 높고, 학습 시간이 길어 반복적인 실험이 어렵다.
- 백테스팅 기능이 **부재**하여 전략의 과거 성과를 객관적으로 검증할 수 없다.
- Tkinter 기반 GUI는 **확장성이 낮고** 웹 기반 서비스로 전환이 어렵다.
- 기술적 지표 산출, 전략 신호 생성, 성과 평가 등의 기능이 **파이프라인으로 연결되지 않는다.**
- 멀티 종목 분석이 불가하여 **포트폴리오 관점의 전략 수립이 어렵다.**

#### 1.3 필요한 요구사항

**가) 데이터 파이프라인**

- KRX 공식 데이터 기반의 안정적인 일봉(OHLCV) 수집 기능
- 증분 업데이트를 지원하는 데이터 저장 체계
- 다종목 배치 수집 및 스케줄링

**나) 기술적 분석 및 전략**

- RSI, MACD, 볼린저밴드, ATR, OBV 등 주요 기술적 지표 산출
- 골든크로스, RSI 과매수/과매도, 볼린저밴드 돌파 등 룰 기반 전략
- LightGBM 기반 ML 매매 신호 예측

**다) 백테스팅 및 성과 평가**

- 수수료·슬리피지를 반영한 현실적 백테스팅
- 총 수익률, CAGR, 샤프비율, MDD, 승률 등 핵심 성과 지표
- KOSPI/KOSDAQ 벤치마크 대비 성과 비교

**라) 시각화 및 사용자 인터페이스**

- 가격 차트에 지표·신호를 오버레이하는 인터랙티브 차트
- 백테스팅 결과 리포트 대시보드
- 전략 파라미터 조정 UI

#### 1.4 프로젝트의 필요성

가) 기존 LSTM 기반 시스템은 단일 종목 가격 예측에 국한되어 있어, 실질적인 매매 의사결정까지 이어지지 못하는 한계가 있다. 이를 전략 기반의 체계적인 퀀트 시스템으로 전환함으로써 데이터 수집부터 성과 평가까지 일관된 워크플로우를 제공할 수 있다.

나) CPU 환경에서 동작하는 경량 시스템을 구축하여 별도의 GPU 인프라 없이도 퀀트 전략을 실험하고 검증할 수 있는 환경을 마련한다.

다) 인터페이스 기반 확장 설계를 적용하여 향후 실시간 트레이딩, 암호화폐, 해외 주식 등으로의 확장 기반을 확보한다.

### 2. 프로젝트의 범위(요약)

본 프로젝트는 한국 주식 시장(KOSPI/KOSDAQ) 대상의 일봉 기반 스윙 트레이딩 시스템을 구축하는 것을 목표로 하며, 4개의 프로토타입 단계(P1~P4)로 나누어 점진적으로 개발한다.

#### 2.1 주요 개발 범위

**가) P1 - 데이터 파이프라인 + 기본 API (1.5주)**

단일 종목(삼성전자)을 대상으로 pykrx 데이터 수집, PostgreSQL 저장, FastAPI REST API를 구축하여 전체 시스템의 기반을 마련한다.

**나) P2 - 기술적 지표 + 룰 기반 전략 + 시각화 (1.5주)**

기술적 지표를 산출하고 룰 기반 전략으로 매매 신호를 생성하며, Streamlit 대시보드를 통해 차트와 신호를 시각화한다.

**다) P3 - 백테스팅 + ML 모델 (2주)**

vectorbt 기반 백테스팅 엔진과 LightGBM 분류 모델을 구현하여 전략의 성과를 정량적으로 검증하고, 룰 기반 vs ML 전략을 비교 분석한다.

**라) P4 - 멀티 종목 지원 + 대시보드 완성 (1주)**

단일 종목에서 다종목 워치리스트 관리로 확장하고, 전체 대시보드 UI/UX를 완성한다.

#### 2.2 범위 제외 항목

- 실시간 자동매매 (HFT, 분봉 전략 포함)
- 모바일 애플리케이션
- 해외 주식 및 암호화폐 (향후 확장 예정)
- 증권사 API 연동을 통한 실주문 실행

## II. 프로젝트 수행 내용

### 1. 목표시스템의 구성도

```
┌─────────────────────────────────────────────────────────┐
│                    사용자 (브라우저)                       │
└──────────────────────┬──────────────────────────────────┘
                       │ HTTP
┌──────────────────────▼──────────────────────────────────┐
│              Frontend (Streamlit → React)                │
│   - 종목 선택 / 차트 시각화 / 전략 파라미터 조정           │
│   - 백테스팅 결과 리포트 / 대시보드                       │
└──────────────────────┬──────────────────────────────────┘
                       │ REST API
┌──────────────────────▼──────────────────────────────────┐
│                Backend (FastAPI + Uvicorn)               │
│  ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌────────────┐  │
│  │  Stock   │ │  Price   │ │ Strategy │ │  Backtest  │  │
│  │ Domain   │ │ Domain   │ │ Domain   │ │  Domain    │  │
│  └─────────┘ └──────────┘ └──────────┘ └────────────┘  │
│  ┌──────────────┐ ┌──────────┐ ┌─────────────────────┐  │
│  │  DataSource   │ │Indicator │ │    ML Domain        │  │
│  │  (pykrx)     │ │ Domain   │ │   (LightGBM)        │  │
│  └──────────────┘ └──────────┘ └─────────────────────┘  │
└──────────────────────┬──────────────────────────────────┘
                       │ SQLAlchemy ORM
┌──────────────────────▼──────────────────────────────────┐
│            Database (PostgreSQL 16 on Docker)            │
│   stocks │ daily_prices │ indicators │ signals           │
│   watchlist │ backtest_results │ backtest_trades         │
│   ml_models                                             │
└─────────────────────────────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────┐
│               외부 데이터 소스                             │
│   - pykrx (KRX 공식 일봉 데이터)                         │
│   - (향후) yfinance, 증권사 API, CCXT                    │
└─────────────────────────────────────────────────────────┘
```

**가) Frontend (Streamlit → React)**

사용자에게 종목 선택, 차트 시각화, 전략 파라미터 조정, 백테스팅 결과 리포트를 제공하는 웹 인터페이스이다. 초기에는 Streamlit으로 빠르게 프로토타이핑하고, 향후 React로 전환한다.

**나) Backend (FastAPI)**

모든 비즈니스 로직을 처리하는 핵심 서버이다. 도메인별로 분리된 계층 구조(Router → Service → Repository → Entity)를 적용하며, 데이터 수집, 지표 산출, 전략 실행, 백테스팅 등을 REST API로 제공한다.

**다) Database (PostgreSQL 16)**

종목 정보, 일봉 데이터, 기술적 지표, 매매 신호, 백테스팅 결과 등 모든 데이터를 저장·관리한다. Docker Compose로 운영하여 개발 환경의 일관성을 확보한다.

**라) 외부 데이터 소스**

pykrx를 통해 한국거래소의 공식 일봉(OHLCV) 데이터를 수집한다. DataSource 인터페이스(ABC)를 적용하여 향후 yfinance, 증권사 API 등으로 확장 가능하도록 설계한다.

#### 1.3 모의투자 및 자동매매 기반

#### 1.4 교육 및 포트폴리오

## IV. 기타

### 1. 주요 고려사항 및 리스크

#### 1.1 데이터 품질 및 안정성 문제

pykrx는 KRX 공식 데이터를 제공하지만, 서버 점검이나 장애 시 데이터 수집이 중단될 수 있다. 또한, 주가 데이터의 수정(액면분할, 유상증자 등)이 소급 적용될 경우 기존 저장 데이터와 불일치가 발생할 수 있다.

#### 1.2 백테스팅의 한계 (과적합 위험)

과거 데이터에 최적화된 전략이 미래 시장에서 동일한 성과를 보장하지 않는다. 전략 파라미터의 과도한 최적화(overfitting)는 백테스팅 성과와 실제 성과 간의 괴리를 유발할 수 있다.

#### 1.3 외부 라이브러리 의존성

pykrx, vectorbt, LightGBM 등 핵심 기능이 외부 오픈소스 라이브러리에 의존하고 있어, 라이브러리의 버전 변경이나 지원 중단 시 시스템에 영향을 줄 수 있다.

#### 1.4 단일 개발자 리스크

프로젝트 전 과정을 1인이 수행하므로, 특정 기술 영역에서 병목이 발생할 경우 전체 일정에 영향을 미칠 수 있다.

---

### 2. 리스크 관리 방안

#### 2.1 데이터 무결성 확보

수집 시 데이터 검증 로직을 적용하고, 수정주가 변경 시 영향받는 기간의 데이터를 재수집하는 메커니즘을 마련한다. pykrx 장애 시 재시도 로직과 에러 로깅을 통해 안정적인 수집을 보장한다.

#### 2.2 과적합 방지

Walk-forward 검증 방식을 적용하여 미래 정보 유출(look-ahead bias)을 방지한다. 학습 데이터와 검증 데이터를 시간순으로 엄격히 분리하고, 벤치마크 대비 성과를 함께 비교하여 전략의 실질적 유효성을 판단한다.

#### 2.3 라이브러리 의존성 관리

핵심 외부 기능에 인터페이스(ABC)를 적용하여 특정 라이브러리와의 결합도를 낮춘다. DataSource, Strategy, BacktestEngine 인터페이스를 통해 구현체를 교체할 수 있도록 설계한다.

#### 2.4 일정 관리

프로토타입 단계별로 명확한 산출물과 검증 기준을 설정하고, 각 단계 완료 시 동작하는 시스템을 확보하여 일정 지연 시에도 이전 단계까지의 성과를 보존한다.
